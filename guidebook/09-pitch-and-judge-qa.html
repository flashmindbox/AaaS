Chapter 09

Pitch, Q&A & Roadmap

Everything you need to defend the project in a hallway, at the booth, or in front of the panel — the hooks, the numbers, the hard questions, and an honest map of what’s done versus what’s next.

The pitch, two lengths

15 seconds

“Every government website makes citizens with disabilities ask someone else for help. We built one shared, Odia-first accessibility layer any institution can switch on in a day — the UPI of accessibility.”

60 seconds

“Odisha has 42 million Odia speakers and 21 lakh persons with disabilities, yet government portals are English-first and unusable for them. Today every institution is expected to fix this alone, and almost none do. Our insight: accessibility is infrastructure, not 200 separate projects. So we built a single platform — Odia voice, dictation, translation, a dyslexia-aware reading mode, accessible exams, and a WCAG compliance dashboard — behind one API. An institution adds one line of code and its users get all of it. It’s open-source, runs on-prem inside India for DPDP compliance, and it’s working today. We’re asking you to help us pilot it at one Odisha institution.”

Hard questions, honest answers

“Isn’t this just an accessibility overlay like AccessiBe?”

No. Overlays bolt onto broken HTML at run-time and the disability community criticises them. We provide an opt-in assistive layer the user controls and a WCAG audit tool that helps the institution fix the root cause. We make sites better, we don’t paper over them.

“You didn’t train the AI models — where’s the innovation?”

Correct, and deliberate. The models (MMS-TTS, IndicTrans2, IndicWav2Vec) are open and excellent; reinventing them would be foolish. The hard, valuable work is the integration: a reliable multi-tenant platform, the Odia-specific design rules, graceful failure, DPDP controls, and one-line adoption. UPI didn’t invent banks — it connected them.

“How do I know it actually works for Odia?”

Watch the demo: it reads real Odia aloud and translates a live page into correct Odia through our own engine. We’re also honest about limits — standard Odia is strong; rural dialects are future work, not a solved claim.

“It’s a hackathon project — is the rest vapourware?”

Check the repository: a real threat model, a DPDP data-flow map, a machine-enforced WCAG checklist, CI, and an SBOM are all there. The six components run today. We show what’s built and label what’s roadmap.

What’s built today vs what’s next

  • Done · Foundations & working slice
    Design system, CI, threat model, DPDP map, WCAG harness — plus all six components running: TTS, STT, translation, gateway, exam, admin.
  • Done · Real websites
    Browser extension + widget verified injecting and reading aloud on live third-party sites; translation routed through our own gateway.
  • Next · Pilot hardening
    Real sign-in (Keycloak/DigiLocker), a database for tenants & keys, rate-limits, and a commercially-licensed Odia voice.
  • Next · Language & assistance breadth
    More Indian languages, a screen-reader overlay, sign-language avatar, and a public accuracy benchmark per language.
  • Later · Scale & certification
    Reference deployment at OCAC Bhubaneswar, ISO 27001 / CERT-In, and a state-wide onboarding playbook.

Weaknesses we state up front

Naming these earns more trust than hiding them: no professionally-trained accessibility auditor on the core team yet; no disabled Odia-speaking user testing done so far; no signed pilot institution (targets identified); and rural-dialect speech is unproven. Each is openly sequenced into the roadmap.
